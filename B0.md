# B0 — The `count` trap

With `count`, Terraform identifies each bucket by its numeric position, not by the
landlord account ID. The seeded state contains four instances:

- `landlord_media[0]` -> `la-001`
- `landlord_media[1]` -> `la-002`
- `landlord_media[2]` -> `la-003`
- `landlord_media[3]` -> `la-004`

If `la-002` is removed from the middle of the input list, the desired list becomes
`[la-001, la-003, la-004]`. Terraform still matches instances by index:

- Index 0 remains `la-001`.
- Index 1 changes from `la-002` to `la-003`; because the bucket name changes, the
  S3 bucket must be replaced.
- Index 2 changes from `la-003` to `la-004`; that bucket must also be replaced.
- Index 3 (`la-004`) is now beyond the desired count and is planned for destruction.

So the plan shows a replacement cascade for the shifted buckets plus a destroy for
the final instance. This is dangerous because the buckets hold landlord media.
An index shift can cause Terraform to replace or destroy buckets belonging to
landlords that were not removed, risking data loss, downtime, and unexpected cost.

**Fix:** use `for_each` keyed by stable landlord account IDs:

```hcl
resource "aws_s3_bucket" "landlord_media" {
  for_each = toset(var.landlord_accounts)

  bucket = "haven-media-${each.key}"

  tags = {
    landlord_account_id = each.key
  }
}
```

Terraform then addresses the buckets as
`aws_s3_bucket.landlord_media["la-001"]`, etc. Removing `la-002` affects only
that key; the other landlord buckets keep their identity.

When migrating an existing `count` resource to `for_each`, add explicit
`moved` blocks (or perform equivalent reviewed `terraform state mv` operations)
for every existing instance so Terraform understands the address change. Review
the plan before applying, and protect data-bearing buckets with appropriate
backup, retention, and deletion controls. `for_each` prevents index-shift churn;
it does not by itself make intentional bucket deletion safe.
