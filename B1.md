# B1 — The Glacier cost gotcha

What's the actual cost impact of an early deletion after archival? How would you redesign the
lifecycle so this stops quietly costing more than budgeted?

## Cost impact

`lifecycle.tf` transitions listing photos to `GLACIER` (S3 Glacier Flexible Retrieval) at day 30.
That storage class has a minimum storage duration of 90 days, and deleting an object earlier is
still billed for the remaining days. In the scenario (archived day 30, seller requests deletion
day 40, deleted immediately) the photo sat in Glacier for 10 days but is charged for the
remaining ~80 days of minimum storage as well, plus the one-time transition request fee. The
deletion saves nothing, and the archival was a net cost compared with leaving it in Standard.

It is "quiet" because the deletion flow is application-level and not modelled in Terraform, so
nothing in a plan or the lifecycle rule shows the conflict. The 30-day transition and the
30-day deletion SLA overlap by design.

The 90-day minimum is from AWS's documented S3 behaviour; I did not look up current prices, so
the dollar amount is not calculated here. Check it against the AWS pricing page.

## Lifecycle redesign

1. Do not transition an object while a deletion request may still arrive or is pending.
2. Add an application-managed retention eligibility check. The application sets an object tag
   (for example `archive_eligible=true`) only once the listing is confirmed safe to archive.
3. Filter the lifecycle `transition` rule on that tag, so only confirmed-eligible objects move
   to Glacier. Objects with a pending deletion request are never archived.
4. Keep the archival delay long enough that most deletion requests land before the transition.
   The right number of days needs the real deletion-request timing data, which I don't have.

**Not done:** I have not changed `terraform/lifecycle.tf`; this is the design only.
