  1. Validation chain

  The model only stores the upward link at each step, so you resolve the chain
  by lookup:

  report.tenant_id -> Tenant.id            (tenants list)
  tenant.property_id -> Property.id        (properties list)
  property.landlord_account_id == actor.landlord_account_id

  - The boundary is LandlordAccount. Not the tenant, not the property. The
    README says a PropertyManager covers "everything under" their account, so a
    manager can see every property's reports within their own account. The only
    comparison is property.landlord_account_id == actor.landlord_account_id.
  - Tenant and Property carry no landlord ID. Only Property and PropertyManager
    do. You can't shortcut the tenant step.
  - Lookups use ID equality. Don't use object equality or list position.

  2. Fail-closed behaviour and edge cases

  Return False when any of these hold:

  ┌────────────────────────────────────┬────────────────────────────────────┐
  │                Case                │           Why it matters           │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ Tenant not found for               │ Orphaned report. The stub names    │
  │ report.tenant_id                   │ this one explicitly.               │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ Property not found for             │ Same. The stub names this one      │
  │ tenant.property_id                 │ explicitly.                        │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ actor.landlord_account_id is None  │ "" == "" or None == None against a │
  │ or empty                           │  bad property would grant access.  │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ property.landlord_account_id is    │ Same equality bug from the other   │
  │ None or empty                      │ side.                              │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ Duplicate Tenant or Property IDs   │ next(...) takes the first match,   │
  │ in the lists                       │ which is ambiguous. Deny.          │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ actor or report is None            │ Deny rather than raise.            │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ Empty properties or tenants lists  │ Falls out of "not found".          │
  └────────────────────────────────────┴────────────────────────────────────┘

  - Never trust IDs on the report or actor beyond the lookup chain. Don't derive
    the account from the tenant name or the property address.
  - No exceptions as control flow. A missing record must return False, not
    raise, so callers can't skip the check with a broad except.
  - Return a strict bool. Not a truthy object.
  - Don't leak why access was denied. The function has no way to say, and it
    shouldn't.

  The duplicate-ID and blank-account rules go beyond the spec. They're cheap and
  security-positive, and I'd keep them.

  3. Test cases using the conftest fixtures

  The fixtures give property_managers, properties, tenants and
  screening_reports. Seed data has pm-001/la-001 and rep-001 (ten-001,
  prop-001), plus pm-002/la-002 and rep-002.

  Required by the spec:
  1. pm-001 on rep-002 is denied (cross-account).
  2. pm-001 on rep-001 is allowed (same account).

  Worth adding:
  3. pm-002 on rep-001 is denied (the reverse direction), and pm-002 on rep-002
  is allowed.
  4. Orphan tenant: build a report with tenant_id="ten-999". Expect denied.
  5. Orphan property: use a Tenant(property_id="prop-999") appended to a local
  copy of the tenants list. Expect denied.
  6. Blank account IDs: a manager with landlord_account_id="" against a property
  with "" is denied.
  7. Empty properties and empty tenants lists are denied.
  8. Duplicate property IDs, with conflicting accounts, are denied.

  Notes:
  - Build the extra objects locally with dataclasses.replace or direct
    construction. The models are frozen and the fixtures return shared
    module-level lists.
  - Don't mutate the fixture lists. Use [*tenants, extra].
  - Run the tests against a version with the cross-account check deleted. Test 1
    should then fail.

  4. Recommended implementation

  The function is about 10 lines and needs no helpers, no new files and no new
  dependencies:

  1. Return False if actor or report is None, or if actor.landlord_account_id is
     falsy.
  2. Collect the matching tenants: [t for t in tenants if t.id == 
     report.tenant_id]. Return False unless exactly one matches.
  3. Do the same for the property, matching on tenant.property_id.
  4. Return property.landlord_account_id == actor.landlord_account_id. The
     earlier falsy check on the actor makes a blank-to-blank match impossible.
     If the property's ID is blank, it can't equal a non-blank actor ID.

  Keep the existing signature and don't touch models.py or seed_data.py.

  Pushback (ultra): don't add a landlord ID to Tenant or ScreeningReport to
  shortcut the lookup. Those files are protected, and the denormalised ID would
  be a second source of truth that can disagree with the real chain.
